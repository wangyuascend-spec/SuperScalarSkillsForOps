01 · 它解决什么问题

普通专家并行中，专家固定归属某个 rank。热门专家的路由需求集中时，该 rank 接收大量 token，其他 rank 可能空闲。MoonEP 允许在其他 rank 复制专家权重，让多个实例分担同一专家的计算。

规划目标：在各 rank 输入形状相同、路由计数正确的前提下，让每 rank 的计划处理量等于 N=S×K。固定副本槽是否足够，是额外的可行性条件。

plan 处理计数、放置和路由元数据。hidden 搬运交给 ElasticBuffer.dispatch，权重预取交给 prefetch_weight，训练时副本权重梯度由 reduce_grad 归并。

router → plan → dispatch → prefetch_weight → 专家计算 → combine
          ├─ vtopk：虚拟路由
          ├─ cu_seqlens：分组边界
          └─ experts_to_copy：副本预取清单

02 · 输入输出与数据契约

关于 rank、S 和 K：rank 是 EP 组内进程编号，通常一个进程对应一张 NPU 卡。当前实现要求同一 EP 组内各 rank 的 S、K 一致；专家选择和每专家负载可以不同。该跨 rank 形状条件由调用方保证。

R 为 rank 数，E 为专家数，epn=E/R；每 rank 输入 S 个 token，每 token 选择 K 个专家，展开为 N=S×K 份路由。

dst_n, cu, etc, src_n, vtopk = moonep_plan(context, tpe, topk)
张量形状 / 类型当前实现含义
tokens_per_expert（tpe）[E] / int32输入：本 rank 发给各专家的份数，应与 top-k 直方图一致。
topk_experts_sk[S,K] / int32输入：真实专家 ID，按 token、k 顺序展开。
cu_seqlens（cu）[2·epn] / int32输出：本 rank 各专家/副本槽的累计结束位置，没有开头的零。
experts_to_copy（etc）[R,epn] / int32输出：各 rank 的远程专家清单，专家 ID 升序，空槽 -1。
vtopk[N] / int32输出：合法规划下位于 [0,2E) 的虚拟专家编号。
dst_n / src_n[N] / int32全零占位，未计算真实落位；同 N 下二者返回同一个缓存张量，应视为只读。

入口：moonep_plan.py 第 1008–1080 行。张量须位于 NPU；入口显式检查 int32、E 上限和 E%R，其他条件有部分依赖调用方。

03A · 七个 kernel：逐个看输入、输出和实现

以下用源码中的 gm_* 名称标识参数。gm 表示全局设备内存（GM）中的张量；ub 表示当前计算块使用的片上统一缓冲区（UB）。 除通信上下文和字节传输缓冲外，下列工作表均为 int32。

统一记号：me 为当前 rank；C 为 chunk 大小；nc=N/C；bd 为 Count/Assign 的 block 数；bdp 为 GreedyInit/Pfx 的 block 数。源码分别选取 nc、E 的不大于 32 的因子，保证任务可以整除分配。这里的 block 是设备计算任务块，不是 rank，也不应直接等同于某个固定物理核心。

启动前准备：Python wrapper 分配或复用 workspace，将本 rank 的 top-k 展平后以设备侧 copy_ 写入 topk_all[me,:]，分配本轮 epoch 标量 gm_flag，再调用编译程序。每个 rank 都执行自己的这套七阶段。

每个 block 整表载入 dem 到 UB，逐专家使用 SIMT 单线程求和。rem/order 按单行 tile写回 GM，避免源码注释提到的动态多行 tile 编译问题。零需求专家也登记 home=1，但其 rem 为零。

免原子的原因：不同 block 写不同专家行和不同 loads_part 行，不争抢同一个负载计数。下一阶段统一求和即可。

③ Greedy：决定各实例份额，并产出本 rank 的分组边界

_MoonepPlanGreedyKernel · 第 274–410 行 · 启动 1 个 block

方向参数 / 形状含义 / 后续消费者
输入并覆写gm_rem [E,R]读初始布局，写均衡后的专家份额；Pfx 消费。
输入并覆写gm_order [E,R]记录 home 与新副本的顺序；Tables、Pfx 消费。
输入gm_loads_part [bdp,R]初始化阶段的各 block 负载贡献。
输出gm_cu [2epn]当前 rank 专家视图的累计结束位置，是最终返回结果之一。
  1. 将 rem、order、loads_part 载入 UB。先对 loads_part 按 block 求和，得到 loads[R]。
  2. 计算 cap=Σloads/R。相同 S、K 且计数正确时，cap=N。
  3. 在一个 vf(mode="simt",thread=1) 区域内完成有数据依赖的贪心循环：找最忙 src、最闲 dst、src 上份额最大的专家，转移 min(超载量、空闲量、专家份额)。
  4. 首次在 dst 承载专家时，赋 order[e,dst]=当前实例数+1；home 一直占顺序 1，不会因份额降为零被移除。
  5. 构造当前 rank 的 sizes：前 epn 行取本地专家的 rem；后 epn 行按专家 ID 升序填入 order[e,me]≥2 的副本份额，然后累加得到 cu。
  6. 把 rem、order、cu 写回 GM。loads 和 sizes 只是 UB 临时状态，没有对应的最终输出表。

为什么单 block：每次移动都会改变下一轮 argmax/argmin，当前实现选择串行维护全局状态。只保护副本槽写入，不在贪心选择时约束槽数，相关风险见第 08 节。

上面是合并表达的等价逻辑；源码实际分两次扫描，先填 jrep，再初始化并填 etc。每个 block 读取完整 order，但只写自己 rank 的连续一行，无跨 block 写冲突。

容易混淆的两个“顺序”：order 按同一个专家的实例创建顺序编号，用于划分 token 份额区间；jrep 按同一目标 rank 上的副本专家 ID编号，用于定位权重视图槽。这两种编号不能互换。

⑤ Count：统计本 rank 各 chunk 的专家需求

方向参数 / 形状含义 / 后续消费者

每 chunk 先清 UB 计数表，再载入 C 个专家 ID，用 SIMT 单线程更新直方图，最后写一行 counts。不同 block 负责不同 chunk，因此没有共享计数器。

源码 tile_slice 的坐标是tile 序号：(me,c) 搭配 tile 大小 (1,C)，对应元素起点 (me,c*C)，不是从元素 c 开始读。

03B · 这些 kernel 怎么配合

1. 逻辑依赖不是简单的七段单链

tpe ──→ Exchange ── dem_by_rank ──→ GreedyInit
                   │                   │ rem / order / loads_part
                   │                   ▼
                   │                Greedy ──────────→ cu（最终输出）
                   │                   │ rem / order
                   │                   ├── order ──→ Tables ──→ etc（最终输出）
                   │                   │                └── jrep ──────┐
                   │                   └──────────────┐                │
                   └───────────────────────────────┐  │                │
                                                   ▼  ▼                │
本地 topk ──→ Count ── counts ────────────────────→ Pfx                │
     │                                             │                   │
     │                      pcnt / dpre / vid / ord_rank / ord_end     │
     │                                             ▼                   ▼
     └──────────────────────────────────────────→ Assign ──→ vtopk（最终输出）

Count 只依赖本地 top-k，逻辑上不依赖 Greedy/Tables；Pfx 不读取 Tables 的 jrep；Assign 才把 Pfx 的“该去哪个 rank”与 Tables 的“该 rank 上哪个副本槽”结合起来。这些是数据依赖关系，不表示当前实现已经并发执行独立分支。

2. 当前代码如何保证执行顺序

_moonep_plan_host 第 777 行附近按 A→B0→B→Tab→Cnt→Pfx→Asg 顺序调用七个 kernel，block 数依次是 1、bdp、1、R、bd、bdp、bd。依赖通过 GM 中间表衔接，按编译 host 程序的执行序消费前序结果；没有在 Python 中逐阶段 .item() 或 CPU 回读来衔接。

Exchange 内部才有跨 rank 的计数到达握手。其余六个 kernel 都处理本 rank 的本地工作表；多个 block 通过互不重叠的输出行/chunk 分工，串行贪心阶段独占全局状态。kernel 边界提供阶段衔接，而非让一个 kernel 的 block 在执行中直接读取另一个 block 的未完成结果。

4. 用 K=2 的完整例子走完七阶段

取 R=2、E=4、S=4、K=2。每张卡有 4 个输入 token，每个 token 选择两个不同专家，因此每卡有 N=S×K=8 次“token 交给专家处理”的任务，全组共 16 次，最终目标是每卡处理 8 次。

专家 0、1 原本在 rank 0；专家 2、3 原本在 rank 1。下面用 r0:t3 表示“来源 rank 0 的第 3 个 token”。token 下标从 0 开始。

4.0 输入：每个 token 都选择两个专家

t1       [0,   1]
t2       [0,   1]

tpe ：[4,2,1,1]

例如 rank 0 的 t0 产生两次处理：一次给专家 0，一次给专家 1，所以分别给 tpe[0] 和 tpe[1] 加 1。tpe 的和是 8，不是输入 token 数 4。

源码的真实分块对 N=8 返回 C=8、nc=1、bd=1；E=4 时 bdp=4。以下严格按该配置演示。K=2 展示同一 token 的两条路由，但这个小尺寸只有一个 chunk，因此 pcnt 全零；多 chunk 时的前缀公式仍见第 06 节。

4.1 Exchange：把各卡的 tpe 收集为二维表

                    专家0  专家1  专家2  专家3
dem_by_rank = [
  rank 0 来源：      [ 4,    3,    1,    0 ],
  rank 1 来源：      [ 4,    2,    1,    1 ]
]
按列求和，全局需求： [ 8,    5,    2,    1 ]

两个 rank 都得到这张相同的表。此时只知道输入需要哪些专家，还没有决定将计算分给哪些卡。

4.2 GreedyInit：先让 home 承担全部需求

rem 的列：             rank0  rank1
专家0                     8      0
专家1                     5      0
专家2                     0      2
专家3                     0      1

order = [[1,0], [1,0], [0,1], [0,1]]

block0 初始化专家0 → [8,0]
block1 初始化专家1 → [5,0]
block2 初始化专家2 → [0,2]
block3 初始化专家3 → [0,1]

每个 block 写自己的一行 loads_part，没有多个 block 同时累加一个全局 loads。Greedy 随后汇总，得到 loads=[13,3]。

4.3 Greedy：把专家 0 的 5 次计算交给 rank 1

cap = (13+3)/2 = 8
src = rank0（13次，超载5）
dst = rank1（3次，空闲5）
e   = 专家0（src 上专家0有8次，专家1有5次）
move = min(13-8, 8-3, 8) = 5

均衡后的 rem：         rank0  rank1
专家0                     3      5
专家1                     5      0
专家2                     0      2
专家3                     0      1

order = [[1,2], [1,0], [0,1], [0,1]]
loads = [8,8]

专家 0 在 rank 1 创建副本，order[0,1]=2。此时只决定专家 0 的 8 次计算中，home 处理 3 次、副本处理 5 次；还没逐个挑出具体 token。

当前接收 rank视图槽 0视图槽 1副本槽 0（视图槽 2）副本槽 1（视图槽 3）cu

rank 1专家2：2次专家3：1次专家0副本：5次空：0次[2,3,8,8]

4.4 Tables：给副本安排权重槽

etc = [
  [-1,-1],    # rank0 没有远程专家副本
  [ 0,-1]     # rank1 的副本槽0放专家0
]

jrep [R,E] = [
  [0,0,0,0],
  [0,1,1,1]
]
# jrep[1,0]=0：专家0在rank1的副本槽号为0。
# jrep[1,1..3]=1：它们之前有1个副本专家；它们自身不是副本，
# 这些位置不会被当作它们的副本槽使用。

每 rank 占用 2×epn=4 个虚拟专家编号，映射如下：

rank0：vid 0→真实专家0；vid 1→真实专家1；vid 2、3→空预取槽
rank1：vid 4→真实专家2；vid 5→真实专家3；vid 6→专家0副本；vid 7→空槽

专家0副本的 vid = 1*4 + epn(2) + jrep[1,0](0) = 6

4.5 Count：按本地 chunk 重新统计真实 top-k

每卡展平序列恰好占一个 chunk，Count 的输出都是 [1,4]：

rank0：counts = [[4,3,1,0]]
rank1：counts = [[4,2,1,1]]

这个小例子里 counts 的唯一行恰好等于本地 tpe。真实大输入有多个 chunk，Count 的作用是把总计数拆成 chunk 局部计数，以便后续并行确定全局顺序。

4.6 Pfx：构造“输入序号”和“处理区间”

输入序号前缀：pcnt 表示本卡更早 chunk 的计数；dpre 表示更小来源 rank 的计数。

两卡的 pcnt [E,1] 都是 [[0],[0],[0],[0]]，因为只有一个chunk。
rank0：dpre = [0,0,0,0]
rank1：dpre = [4,3,1,0]  # 正好是来源rank0的tpe

# 例如：rank1 遇到的第一个专家0任务，其全局专家内序号
pos = dpre[0] + pcnt[0,0] + chunk内更早的专家0次数 = 4+0+0 = 4

处理区间表：按同一个专家的实例顺序，用 rem 构造区间：

专家ord_rank [R+1]ord_end [R+1]区间含义快路径 vid
0[0,1,-1][3,8,8]序号 [0,3) 给 rank0；[3,8) 给 rank1-1，走区间查找
1[0,-1,-1][5,5,5][0,5) 全给 home rank01
2[1,-1,-1][2,2,2][0,2) 全给 home rank14
3[1,-1,-1][1,1,1][0,1) 全给 home rank15

两卡得到相同的实例区间表和 vid=[-1,1,4,5]；不同的是 dpre，因为它与当前来源 rank 有关。

4.7 Assign：逐个任务选择实例，写回 K=2 路由

先单独追踪专家 0的 8 次计算。全局顺序先 rank 0 再 rank 1，各来源内按 token/k 排序：

r0:t2 / k0022[0,3)rank0 home / 0

r1:t2 / k0426[3,8)rank1 副本 / 6

4.8 最终核对：按真实专家任务统计，与 cu 完全对应

目标 rank / 槽计算用的真实专家输入来源 token处理次数累计结束位置
rank0 / 0专家0 homer0:t0、t1、t233
rank0 / 1专家1 homer0:t0、t1、t2；r1:t0、t158
rank0 / 2空副本槽无08
rank0 / 3空副本槽无08
rank1 / 0专家2 homer0:t3；r1:t222

rank1 / 2专家0副本r0:t3；r1:t0、t1、t2、t358

两卡输入各 4 个 token，但各自产生 8 次专家任务。均衡后 rank0 处理 3+5=8 次，rank1 处理 2+1+5=8 次，cu 分别为 [3,8,8,8] 和 [2,3,8,8]。这里统计的是专家计算任务数；同一 hidden 可能被同卡两个专家消费，不能直接把它等同于跨卡网络实际搬运次数或去重后的物理缓冲行数。

配合的核心：Greedy 决定“每个实例处理多少”；Tables 决定“实例对应哪个权重槽”；Count/Pfx 决定“每个输入任务的专家内序号”；Assign 将三者合起来，生成 dispatch 使用的虚拟路由。

04 · 贪心均衡：先决定处理份额

初始时，专家 e 的全部需求由其 home rank e//epn 处理：

demand[e] = Σr dem_by_rank[r,e]
rem[e,home(e)] = demand[e]
order[e,home(e)] = 1
loads[r] = Σe rem[e,r]
cap = Σr loads[r] // R

rem[e,r] 表示专家 e 在 rank r 的处理份数。order[e,r] 中，0 表示未承载，1 是 home，2 及以上表示副本创建顺序。随后每轮：

src = argmax(loads)
dst = argmin(loads)
e   = argmax(rem[:,src])
move = min(loads[src]-cap, cap-loads[dst], rem[e,src])

# 必要时登记专家 e 在 dst 上的新副本
rem[e,src] -= move; rem[e,dst] += move
loads[src] -= move; loads[dst] += move

实现最多执行 E 轮，每轮检查是否仍有超载。并列值由升序扫描确定，通常优先较小下标。这里更新的是计划，还没有搬 token 或权重。

例子：把 [12,4] 的初始负载变成 [8,8]

令 R=2、E=4、epn=2、N=8，全局专家需求为 [12,0,2,2]。把专家 0 的 4 份计算分给 rank 1：

rank 0：保留专家 0 的 8 份
专家 0 × 8
cu=[8,8,8,8]
etc=[-1,-1]
rank 1：新增专家 0 的副本
e2 × 2e3 × 2e0 副本 × 4
cu=[2,4,8,8]
etc=[0,-1]

按源码逻辑构造并通过标准 Python 模拟的例子。条形长度表示路由份数；etc 仅展示对应 rank 的一行。

05 · 为什么扩展为 2E 个虚拟专家

每 rank 的逻辑权重视图包含 2·epn 行：前半是本地真实专家，后半是远程专家预取槽，副本槽按真实专家 ID 升序排列。

rank r：[ 本地专家 0 … epn-1 | 副本槽 0 … epn-1 ]

# home 实例
vid = home_rank * (2*epn) + e%epn

# 远程实例，jrep 是目标 rank 上的副本槽号
vid = dst_rank * (2*epn) + epn + jrep[dst_rank,e]

# dispatch 解码
dst_rank  = vid // (2*epn)
local_slot = vid % (2*epn)

前例中，虚拟空间大小是 8：专家 0 的 home 实例编号为 0；rank 1 的本地专家 2、3 编号为 4、5；rank 1 的专家 0 副本编号为 6。原路由到专家 0 的份数按计划分别改写为 0 或 6。

# 示意：容量等其余参数依调用方配置
buf.dispatch(hidden,
    topk_idx=vtopk.view(S,K),
    topk_weights=route_weights,
    num_experts=2*E, ...)
集成关键：vtopk 的本地槽、cu 的分组顺序、etc 的预取槽和权重视图行号必须一致。dispatch 以虚拟专家分组后，GMM 才能取到正确的专家权重。

06 · 怎样并行决定每份 token 去哪个副本

同一专家的来源顺序定义为 (来源 rank, token 下标, top-k 下标) 升序。该专家在各承载实例上的份额，则按 home 在前、副本创建顺序在后排列为连续区间。

pos(e) = dpre[e] + pcnt[e,chunk] + 当前 chunk 内 e 的已出现次数

dpre[e] = 更小来源 rank 对 e 的需求之和
pcnt[e,chunk] = 本 rank 更早 chunk 中 e 的出现次数

# 若 home 处理 8 份，副本处理 4 份
pos ∈ [0,8)  → home
pos ∈ [8,12) → 副本

前缀将跨 chunk 依赖变成查表，各 block 无需争用原子计数，也能得到与按来源顺序逐份扫描一致的实例归属。

Assign 的两项优化

  • 固定 vid 快路径：专家没有远程处理份额时，直接查一个固定 vid。
  • 区间缓存：为每个慢路径专家维护当前位置、当前区间结束值和当前 vid；只有跨区间时才扫描 ord 表重新定位。

因此多数 token 不必逐个扫描全部 rank。不过 chunk 内仍存在串行依赖，每 chunk 也有重建 O(E) 状态的成本。

07 · 缓存与执行顺序

  • 编译缓存：键为 (S,K,E,R,me)。rank 在 trace 时固化，必须进入键；编译锁保护模块级参数与编译过程。
  • workspace：context 按形状单槽复用中间表。同流顺序保护覆写，跨流切换通过事件等待串行化。
  • 本地 top-k 拷贝：Python 发起设备侧 copy_，并非 CPU 回读；只消费当前 rank 行，但 workspace 仍分配 [R,N]。
  • epoch 握手：计数与 ready flag 发送到对称内存，接收端轮询 flag 达到本轮阈值；各 rank 须遵守一致调用顺序。
  • 通信器分离：moonep context 与 ElasticBuffer 使用独立通信器，避免对称堆布局相互覆盖。
  • 延迟结果检查：plan 返回前不回读 cu 尾值，把检查留到 prefetch/reduce 尾部。这避免了该处 D2H 同步，但不表示首次编译、分配等 host 工作没有耗时。

参考 moonep_plan.py 第 752–1005 行，以及 moonep_context.py 第 194、265、412 行附近。

08 · 实现边界与需要改进的地方

模拟已复现

1. 贪心没有把副本槽数量纳入约束

每 rank 只预留 epn 个副本槽，但贪心只看负载。即使份额可以均衡，槽数仍可能不足。

R=3，E=3，epn=1；全局需求=[43,21,41]；cap=35
第 1 轮：专家 0 从 rank 0 分出 8 份给 rank 1
第 2 轮：专家 2 从 rank 2 分出 6 份给 rank 1
最终 loads=[35,35,35]
rank 1 需要两个副本，但只有一个槽。
rank 1 的 cu 尾值=21+8=29，遗漏第二副本的 6 份。

cu 和 etc 有写前保护，但 Assign 没有对应的超槽编码检查。本例第二副本的 vid=1×2+1+1=4，会被解码到 rank 2 本地槽，造成错误目标路由。

当前报警延迟到后续 prefetch/reduce，dispatch 可能已执行。建议让贪心感知槽容量，或在产生可消费路由前输出并处理显式失败状态。
辅助函数实测 / 静态容量分析

2. 奇数 N 可能使分块退化、前缀表膨胀

chunk 从 2 的幂开始，逐次减半直到整除 N；奇数 N 会降到 1，block 数还须整除 chunk 数。

Nchunkncblock_dim
6553620483232
655371655371

Pfx/Assign 将完整 counts 或 pcnt 表载入 UB。N=65537、E=8 时，单张 int32 表约 2 MiB，超过源码注释所述 256 KiB UB 预算。具体编译/运行失败形态仍需设备确认。

建议使用有界 chunk 数、带尾部掩码的分块，或分片载入中间表。

静态容量分析

3. E、R 的独立上限不能代表所有组合都可运行

E≤1024、R≤64 是显式上限。但在最大组合下，Greedy 的 rem 和 order 两张 int32 表就占 512 KiB，未计其他缓冲。其他阶段也有整表载入与多 block 重复读取。应结合各阶段 UB 总预算限制组合或重构表的组织。

源码控制流确认

4. 延迟溢出检查只保存最新一次 plan

pending_overflow 是单槽赋值。若依次执行 plan A、plan B，再到检查点，A 的记录会被 B 覆盖。“所有已执行 plan 都得到检查”需要额外调用纪律，当前代码本身没有完整保证。

接口前提

5. 输入合法性与并发条件依赖调用方

入口未全面验证计数和 top-k 一致性、专家 ID 范围、同设备、连续性及非空输入。N=0 时分块函数返回 (128,0,0)，没有合法启动保护。全零占位缓存仅按 N 键控，也不应把 workspace 复用理解为支持任意多线程并发。

分组内各 rank 的 S、K 和调用顺序须一致，否则 cap=N、前缀分配和 epoch 握手的前提可能不成立。
