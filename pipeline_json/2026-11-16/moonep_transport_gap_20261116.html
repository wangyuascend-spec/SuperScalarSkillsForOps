MoonEP 通信方案与性能差距

2026年11月16日 · cannbot DSL 0.8.0 / URMA 与 PyPTO Pro Window / UB_MEM参考路径 · 最新生产提交 bef6929

结论与证据范围

当前 MoonEP DSL 默认选择 URMA / COMM_PROTOCOL_UBC_CTP。PyPTO 算子使用 Window 的远端 GM 映射与 MTE put/get，已有框架参考源码及历史初始化日志对应 UB_MEM。两者的通信引擎不同，既有耗时差不能全部归因于 kernel 编排。

DSL 结论已只读核对远端实际安装的 cannbot-dsl 0.8.0。PyPTO 通道依据已下载框架源码及历史实际 UB_MEM 初始化记录，本次没有重新核对远端固定安装版的完整运行时，也没有采集物理链路追踪。该差别必须保留在结论中。

发送端 payload 的实际数据路径（2026年11月17日补充）

当前 PyPTO 发送前明确把 tpe 从 GM 加载到本地 UB tile，再通过 MTE3 put 写入远端 Window GM。DSL 的 URMA put 直接接收原本位于 GM 的 gm_tpe 作为源，算子源码中没有为这次远端发送先做一份 UB→GM staging。

对性能归因的影响

PyPTO 有一项可见的 GM→UB 预载成本；DSL 远端 put 的源已经在 GM，算子不需要为本次远端发送额外构造一份 GM staging。不能据此直接计算该步骤贡献了多少微秒，也不能把 URMA 描述成必然多一次 UB→GM 复制。原通信段样本同时包含准备、同步、通知和 rank 到达等待，必须按真实阶段边界解释。

原分段探针的 preload 标记只代表发射和依赖设置。MTE2→MTE3 依赖不等于 scalar 观察到全部搬运完成，不能把该标记附近约几个周期当作真实 load 耗时；发送阶段可能仍包含预载完成等待。

下一步公平对照方案

  1. 固定同机、同工具链、R/S/K/E、seed、路由、实际AIV数、合法输入与默认校验策略，保存实际加载SO及协议配置。
  2. 采用同一payload和ready语义，分别测UB_MEM与URMA引擎；首先确认PyPTO显式channel/write能力及当前版本签名，不能仅改名字声称切换。
  3. 每种引擎检查交替payload、epoch、错位启动、连续异步复用，完整算子五输出逐元素一致。
  4. 在同一设备锁内交替采样，预热后保留至少20个样本，报告每rank配对比、分位、胜率与长尾。
  5. 单独通信是直接测量，完整融合另测。不得用整体减计算推算通信，不得由独立阶段相加重建融合耗时。

在这组对照前，只能确认实现机制存在差异，不能量化其中多少gap由URMA或UB_MEM本身引起。

## Conclusion and scope

This installed runtime's default configuration selects URMA/UBC_CTP for the inspected MoonEP context. The current PyPTO Window path inspected separately uses UB_MEM remote mapped GM plus MTE put/get. Transport selection is an important additional condition for existing DSL/PyPTO comparisons. Local UB workspace means Unified Buffer, not proof of UBMEM protocol. This is source-level selection evidence, not a new physical-link hardware trace.

The remote source SHA256 was not recorded in this inspection and is intentionally not fabricated. Source lines were printed from the actual installed package through SSH. Historical local framework copies alone were not used to infer DSL default protocol.

此前通信分析主要聚焦kernel步骤，遗漏了默认协议选择这一条件。新发现要求把传输引擎与编排差异同时纳入解释，已有数值和耗时仍有效，但其根因归属应重新限定。
